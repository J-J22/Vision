AI Build Team Plan
Project plan · draft v2

An AI team that builds your app, from first conversation to live website

You describe the app you want, for example a marketplace. AI agents first get to know you and interview you in language that fits your level. Then they split the work like a real dev team, coordinate as coworkers, test and break the app on purpose, fix what fails, and deploy it.

Stage 1 · Discovery

Interview the user, at their level

Discovery starts with the person, not the app. The first few questions find out who they are, and every question after that adapts to their answers.

  • What do you do? (founder, student, developer, designer, business owner)
  • Have you built or launched an app before? Do you code?
  • Who is the app for, and what problem does it solve?
  • Budget, deadline, and whether you have a preferred tech stack

The same question, asked three ways

Non-technical

"When a buyer pays, should the money go straight to the seller, or should your platform hold it until the buyer confirms they got the item?"

Some tech

"Do you want escrow-style payments with delayed payouts to sellers, or instant transfers? This affects which Stripe setup we use."

Developer

"Stripe Connect Express with manual payouts and an order-confirmation webhook, or direct charges? Any platform fee model?"

When a topic is deep, the agent explains it with an everyday example first, offers choices, and marks the one it recommends. Anything the user doesn't care about gets a sensible default that is written down so it can be changed later.

Stage 1 · coverage

Everything Discovery must cover

A full-stack website has the same checklist every time. Discovery keeps asking or defaulting until every row is filled.

AreaFor a marketplace, this means
Users & rolesBuyers, sellers, admins; what each can see and do
FeaturesListings, search and filters, cart, orders, reviews, messaging, disputes; MVP vs later
Pages & UIHome, listing page, seller dashboard, checkout, admin panel; web, mobile or both
DatabaseTables for users, listings, orders, payments, reviews, messages; how they connect; image storage
APIs & endpointsEvery endpoint (e.g. POST /listings, GET /orders/:id), who can call it, errors, pagination, rate limits
Login & securityEmail, Google or phone login; permissions; protecting personal and payment data
PaymentsCheckout, platform fee, seller payouts, refunds, escrow
IntegrationsEmail and SMS, maps, search engine, push notifications, analytics
Scale & speedExpected users, peak traffic, which countries, uptime target
Hosting & deployCloud provider, staging and production, domain, SSL, automated releases
MonitoringLogs, error alerts, backups
LegalTerms, privacy policy, GDPR or local rules, tax on sales

App-type knowledge. The system keeps a checklist for each kind of app. For a marketplace, it already knows to ask about seller verification, fake listings, refunds, disputes and reviews, even if the user never mentions them. Normal users skip these details when they copy an app. That is why this checklist matters.

Stage 2 · Blueprint

One plan everyone builds from

When Discovery ends, the answers become the Blueprint. The user approves it before any code is written. Each agent then reads the part that concerns its job.

FileWhat it holds
blueprint.yamlThe full plan in a structured format agents can read
product.mdThe same plan in plain English for the user and team
api-contractEvery endpoint with inputs and outputs (OpenAPI format)
db-schemaTables, columns and relationships
decisions.mdEach big choice and why it was made
assumptions.mdEvery default the system picked, so the user can change any of them
Stage 3 · Team build

The agent team

orchestrator

Project manager. Breaks the Blueprint into tasks, assigns them, tracks dependencies.

architect

Chooses the structure and writes the API contract and DB schema.

database

Builds tables, migrations, indexes and sample data.

backend

Writes the APIs, business logic, payments and login.

frontend

Builds the pages and connects them to the APIs.

qa / tester

Writes tests and hunts for edge cases.

security

Checks login, permissions, data leaks and common attacks.

reviewer

Reviews every change before it is merged.

devops

Sets up servers, automated releases, monitoring and rollback.

Stage 3 · coordination

How agents work as coworkers

Shared task board

Every task has an owner, a status, and the tasks it depends on. Agents pick up work as soon as what it depends on is done.

Agree on contracts first

The API contract and DB schema are fixed before coding. Then frontend and backend work in parallel; frontend uses fake data until the real API is ready.

Talk to each other

Agents message each other directly ("the orders endpoint needs a seller_id filter"). If a change affects others, the orchestrator updates the plan.

Review before merge

No agent merges its own code. The reviewer agent and the tests must both pass.

Shared memory

Decisions, open problems and progress live in one place every agent can read, so nobody repeats work or contradicts the plan.

Ask the user when stuck

If agents disagree or need a product decision, the question goes to the user in plain language, at their level.

Stage 4 · Test & break

Find every edge case before users do

The QA and security agents try to break the app on purpose. They use a library of known edge cases, plus ones specific to this app type.

Race conditionTwo buyers pay for the last item at the same moment
Payment failureCard declined halfway, webhook arrives twice, refund after payout
Bad inputEmpty fields, emoji and other scripts, 50MB image, negative price
PermissionsA buyer edits someone else's listing by changing the ID in the URL
Load1,000 users search at once; slow network on mobile
AbuseSpam listings, fake reviews, bots, login brute force
  1. 1

    A test fails

    The failure, logs and steps to reproduce go on the task board.

  2. 2

    The owner agent fixes it

    The agent that wrote that part debugs it and writes a test so the bug can't come back.

  3. 3

    Everything reruns

    The full test suite runs again to check the fix broke nothing else.

    ↻ after 3 failed tries, escalate to the architect or the user
Stage 5 · Deploy

Ship it safely

  • Deploy to a staging copy first. The user clicks through it and approves.
  • Then deploy to production with automated releases (CI/CD) and infrastructure written as code.
  • Monitoring and error alerts are on from day one. A bad release rolls back automatically.
  • After launch, real errors and feedback go back to the team as new tasks.
Your question

What data and background knowledge the agents need

No model training needed to start. Current AI models already know how to code. What they need is the right knowledge and memory handed to them at the right time. Training or fine-tuning only makes sense later, if logs show the same mistakes again and again.

WhatWhat it isWhy the agents need it
App-type checklistsPer app type (marketplace, social, booking…): features, edge cases, typical database tablesSo Discovery asks the right questions and QA knows what to break
Starter templatesTested project skeletons for the default stack: login, payments, file upload, admin panelAgents start from working code instead of writing everything from scratch
Best-practice libraryDocs on API design, security rules, database patterns, deployment guidesRetrieved and handed to an agent only when relevant (RAG)
Project memoryThe Blueprint, decisions, task board and conversation history for this projectKeeps every agent consistent with the plan
CachesPrompt caching for long shared context; saved results of repeated workCuts cost and speed by a lot, since every agent rereads the Blueprint

Test sets (evals)Sample vague app ideas with the answers a senior engineer would giveMeasures whether a prompt change actually made the agents better
Run logsWhat each agent did, what failed, how long it tookShows where to improve; becomes training data later if needed
Roadmap

Order of building the platform

PhaseGoalDone when
1 · DiscoveryUser profiling, adaptive questions, full coverage checklist, Blueprint outputA vague idea reliably becomes an approved Blueprint
2 · Single builderOne agent builds a working app from the Blueprint using starter templatesMarketplace MVP runs in the sandbox
3 · TeamSplit into specialist agents with task board, contracts, messaging and reviewAgents finish a build in parallel without stepping on each other
4 · Test & breakQA and security agents, edge-case library, debug loopBuilds pass the edge-case suite
5 · DeployStaging, production, monitoring, rollbackOne click from approved staging to a live URL

Building one capable agent before splitting into a team is deliberate. It is much easier to debug, and it shows exactly which jobs are worth giving to a specialist.

Needs a team decision

Open decisions

Default tech stack

Leaning: lock one stack for v1 (e.g. Next.js, Node or FastAPI, Postgres, Docker, AWS). Agents get far more reliable when they always build with the same tools.

Sandbox setup

Leaning: one Docker container per project with its own repo, database and test server.

Agent framework

Leaning: plain LLM API for Phase 1; choose an orchestration approach at Phase 3 once real needs are clear.

Human approval points

Leaning: user approves the Blueprint, staging, and every production deploy.
